## Release blocker and packaging boundary

The fresh Windows production build reproducibly overwrites its isolated `supabase/functions/mcp/index.ts` with a machine-local import beginning `npm:C:\\Users\\ADMIN\\...`. This is not a deployable package import. The 17-stage frontend build does not validate that function's runtime. Evidence: [generated file, line 6](../../outputs/paint-seo-predeployment-2026-10-12/generated-backend.txt) and [build side effects](../../outputs/paint-seo-predeployment-2026-10-12/isolated-build-side-effects.json).

The source checkout's actual backend remains byte-identical to HEAD, SHA-256 `24e7979785bf67d0dd92d7236cd49ffbe3d82830276a9db237ea5f796ebe0aad`. Repository scripts have no deploy command, and documentation does not prove an automatic Supabase deployment. Therefore this blocks a backend-inclusive/whole-workspace publication, not the independently tested static frontend itself.

A frontend release must use fresh assets and the matching generated routing bundle, exclude generated backend and unrelated output collections, and verify the backend remains unchanged after any release build. The tested `dist/_worker.js` equals its generated Cloudflare router; both 404 asset references exist. Do not activate new production infrastructure merely because an artifact exists. See [final integrity evidence](../../outputs/paint-seo-predeployment-2026-10-12/final-integrity.json).
