Concrete release blocker
The unchanged vite.config.ts enables mcpPlugin() in every mode. Installed and locked @lovable.dev/mcp-js is 0.20.1; the preserved HEAD function imports 0.20.0. The installed plugin's externalizeBareAsNpm treats only dot-prefixed and slash-prefixed paths as local. A Windows absolute entry beginning C: is consequently converted to npm:C:\\...\\src\\lib\\mcp\\index.ts. configResolved and buildStart regenerate supabase/functions/mcp/index.ts. The parent QA's fresh isolated 17-stage production build passed but reproduced this invalid Windows import and changed the function hash from 24e7979785bf67d0dd92d7236cd49ffbe3d82830276a9db237ea5f796ebe0aad to 60bffd261bc00a5fa86af69c9c52b2e981c100b6f764c1ea26c08353582b4690. Thus a green frontend build is not evidence that its generated backend is deployable. The implementation's restoration helper is outside the declared production pipeline; another ordinary Windows build will recreate the invalid file. This tooling issue predates the paint change but is a reproducible release hazard now.

Required release boundary: package the checked dist frontend and its matching Cloudflare bundle; exclude Supabase/backend publication. Verify backend SHA-256 remains the preserved HEAD hash after the final build and before packaging. A deployment that actually consumes the generated backend remains NO-GO until the plugin is fixed or that backend is demonstrably excluded. The repository does not establish that every Lovable content publication consumes this Windows-generated file; that should not be asserted from the side effect alone. No backend fix is part of this review.
Evidence: isolated-build-side-effects.json; generated-backend.txt; original implementation build-side-effects/mcp.generated.ts.txt; node_modules/@lovable.dev/mcp-js/dist/stacks/supabase/vite.js lines 74-98, 108-126, 247-252, 275-277.
