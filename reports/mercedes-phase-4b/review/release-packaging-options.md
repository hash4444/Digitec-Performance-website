## Why a partial compiled upload is unsafe

`vite.config.ts` enables a manifest and hashed bundles. The public application entry imports the brand components through its generated dependency graph. Changing the two component chunks changes their names and the entry graph; the old entry would continue to load the old components during SPA navigation. Replacing only server HTML could display new text before hydration and old content after client navigation. Reusing an old hash for changed bytes would invalidate the meaning of that asset identity. Vite documents the manifest as the mapping from source assets to generated hashed filenames; the observed public manifest and entry graph confirm that relationship here. [Vite build manifest](https://vite.dev/config/build-options.html#build-manifest)

The normal pipeline also regenerates all route HTML, the entry, `.vite/manifest.json`, error documents, sitemap and routing support data. Both `404.html` and `404-ar.html` reference that build's entry and CSS; `cloudflare/routing-response-data.js` embeds generated error HTML for a separate router. These references must belong to the same build. Existing shared templates also serve other brands and services, so source scope alone does not prove all generated files remain identical. The parent task separately compares all 1,256 route outputs and metadata.

No hybrid artifact, renamed compiled chunk, hand-edited HTML, edited manifest, copied old sitemap or manually pruned deployment directory was assembled in this review.

That does **not** demonstrate that it executes on public requests: its unknown-path 404 behavior differs from the actual response. `/_headers` returns homepage HTML, so it is not evidence of an active headers configuration.

The local production preview explicitly imports `dist/_worker.js`. Its success proves the prepared local worker's behavior, not existing production edge activation.
